# Аналитика регулярности Speaky

Статус: реализовано локально; проверка и эксплуатационные границы — в [integration doc](../integrations/2026-10-19-habit-analytics.md). Выкат не выполнялся. Пользователь подтвердил три определения: активность — завершённый голосовой ход AI; начало когорты — первый такой ход; длительность — суммарная распознанная речь пользователя за звонок. Остальные детали ниже остаются планом реализации. Проверен код текущей ветки, не состояние PROD.

Цель: видеть повторное использование Telegram Speaky отдельно от регистраций. Добавить блок на `/admin/metrics` и соответствующий раздел Grafana; согласовать retention на `/admin/metrics/streaks`.

## Что уже есть

- `ai-service/app/metrics_v2.py::overview`: дневные множества нормализованных Telegram ID, скользящий WAU, общий retention D1/D7/D30 от первого отправленного голосового.
- `AdminOverviewPage.kt`: недельная аудитория и stickiness 7/30.
- `streaks.py`: недельные когорты D1/D7/D30, но отдельный расчёт с другими правилами зрелости и без объединения исторических форматов ID.
- `CallDashboard.kt`, `analytics/CallAnalytics.kt`: распознанные секунды и границы диалога. Детальные события живут 30 дней; сводка ограничена 50 000 событий.
- Grafana показывает DAU, но дневные количества не позволяют восстановить точный WAU. Есть Prometheus и PostgreSQL datasource для стоимости; доступ к новым данным потребует отдельных разрешений.

## Определения

1. Область: Telegram, нормализованный chat ID. В личном чате это пользователь, групповой чат считается одним ID. Нагрузочный трафик исключается существующим фильтром; старую историю нельзя объявлять полностью очищенной от тестов.
2. Активный день: хотя бы один завершённый голосовой ход AI, включая уточнение при нераспознанной речи. Факт фиксируется до доставки Telegram. `/start`, кнопки и регистрации активностью не считаются. Источник — существующие `metrics:dau:*`, без смены семантики исторического ряда.
3. Все календарные даты — Europe/Moscow. Опорная дата E по умолчанию вчера: последние семь завершённых суток E−6…E. При выборе сегодняшнего дня блок явно помечается как предварительный.
4. DAU(E) — уникальные ID за E. WAU(E) — объединение ID за E−6…E, не сумма DAU. DAU/WAU = DAU(E) / WAU(E). Графики показывают дневные значения, итоговая карточка — значение на E, не среднее отношений за выбранный период.
5. Распределение: каждому ID из WAU посчитать число разных активных дней в том же окне; группы 1, 2, 3, 4–7. Показать число и долю от WAU. Это не длина непрерывного стрика. Сумма групп равна WAU.
6. Когорту строить по первому завершённому голосовому ходу AI в доступной истории. Строки — недели понедельник–воскресенье, последние 8 недель по умолчанию. Возврат Dn — активность ровно на дату первого хода + n, для n=1,3,7. Сохранить доступ к D30. Для каждой ячейки показывать returned / eligible и процент; eligible включает только людей, чей целевой день уже полностью завершился на дату среза. Частично зрелую когорту обозначать явно. Общий retention — отношение сумм, не среднее процентов когорт.
7. Исторический первый наблюдаемый ход не всегда является первым за жизнь. Первую неполную неделю сбора помечать; не представлять её как надёжную новую когорту. Период фильтрует даты входа в когорту, но чтение возвратов продолжается за его правой границей до даты среза.
8. Основная длительность: среднее суммарных распознанных секунд пользователя на закрытый практический звонок с хотя бы одним распознанным голосовым ходом. Подпись «Речь пользователя на разговор», минуты, рядом число звонков. Это не длительность речи AI и не время открытого звонка. Онбординг, пустые открытия и ещё открытые звонки не входят; количество исключённых показывается. Период определяется датой начала звонка, события читаются за весь звонок, включая переход через полночь. Неизвестная длительность не заменяется нулём.
9. Нет зрелых пользователей или знаменатель равен нулю — «—». Подтверждённо пустой полный день — ноль; неизвестное покрытие, ошибка источника и даты до начала сбора — пропуск. Неполное семидневное окно не выдавать за полный WAU.

## Реализация

### 1. Общий расчёт регулярности

- Выделить общий модуль расчёта в AI-service: нормализация ID, календарные окна, группы активных дней, когорты, числители/знаменатели, границы покрытия.
- Использовать его из overview и отчёта стриков; добавить D3. Старый retention от первого отправленного голоса не переименовывать молча: новый блок имеет явную подпись основания когорты, прежний показатель доступен как исторический до согласованного перехода.
- Читать Redis пакетами; кешировать готовый отчёт, не сканировать всю историю на каждый Prometheus scrape. Экспортировать время последнего успешного расчёта и состояние источника; при сбое не возвращать ложные нули.
- Расширить внутренний API и `ClipDtos.kt` совместимыми необязательными полями. Данные UI: опорная дата, timezone, definition version, coverage, daily series, weekly distribution, cohort rows с counts.

### 2. Длительность и долговременные итоги

- Добавить новую Flyway-миграцию для компактной сводки по callId: дата открытия, закрытие, число распознанных ходов, сумма известных секунд, полнота данных. Не сохранять аудио, тексты или username в сводке.
- Идемпотентно обновлять сводку вместе с записью события в одной транзакции, после разрешения event_id-конфликта. Повтор события и Retry не прибавляют секунды заново. Расчёт не зависит от лимита UI в 50 000 событий.
- Первичное заполнение выполнять пакетами только из сохранившихся событий, с повторяемым запуском. Не восстанавливать старую длительность из STT total или времени позднего закрытия. При отсутствии call_open/части событий сводка помечается неполной.
- Сохранять компактные итоги дольше 30 дней (предложение: 365 дней); сырые события продолжать удалять по прежнему сроку. Учесть позднее закрытие, рестарты, потерю событий очереди и пересчёт затронутой даты. Показать доступное покрытие и потери.
- API длительности возвращает сумму секунд и число подходящих звонков, а не только среднее. Отчёт за период делит общую сумму на общее число звонков.

### 3. Самописный дашборд

- На `/admin/metrics` добавить блок «Регулярность»: DAU, WAU, DAU/WAU; дневной график; четыре группы активных дней; таблицу когорт D1/D3/D7; среднее время речи и размер выборки.
- Явно показывать окно недели, дату среза и определение активности. Фильтр дат графика не превращает WAU в уникальных за произвольный период.
- На `/admin/metrics/streaks` использовать общую когортную таблицу. Сохранить продуктовые стрики и их текущие группы без изменения поведения бота.

### 4. Grafana

- Добавить раздел «Регулярность Speaky» с теми же определениями. Готовые WAU, DAU/WAU, группы дней и counts когорт экспортировать из общего кешированного расчёта в существующий Prometheus endpoint.
- Ограничить экспорт: 30 последних дневных окон, 8 недель когорт, фиксированные buckets/offsets. Не помещать chatId, sessionId или callId в labels. Пропуски сопровождать признаками полноты, а не нулевыми значениями.
- Для когорт выбирать последний актуальный снимок, не максимум исторических процентов. Показывать дату среза: выбранный Grafana time range не меняет смысл семидневного окна. Исторические произвольные срезы доступны в самописном отчёте.
- Среднюю длительность читать из агрегатного SQL view по сохранённым сводкам; предоставить Grafana только SELECT на этот view. Формула общая с Ktor: sum(seconds) / sum(calls), одинаковые фильтры и московские даты. Не давать datasource доступ ко всей таблице событий.
- Provisioning, grants и dashboard JSON включить в изменение; применение к окружению — при отдельно согласованном выкатывании.

## Проверка и приёмка

- Детерминированные примеры: повторные ходы за день, старый/новый session ID одного чата, полночь Москвы, пустой день, неполное окно, D1/D3/D7, частично зрелая когорта, отсутствие истории, исключённая нагрузка.
- Ключевые инварианты: группы дней суммируются в WAU; DAU ≤ WAU; returned ≤ eligible; общий retention считается по людям; показатели трёх страниц совпадают для одинакового среза.
- PostgreSQL integration: идемпотентность, повторное заполнение, звонок через полночь, позднее закрытие, неизвестные секунды, сохранение итога после удаления 30-дневных событий; EXPLAIN на репрезентативном объёме.
- Python tests и `:server:test`, `:server:detekt` из `cmp/`; проверить dashboard JSON и реальные SQL/Prometheus запросы в тестовом окружении. Сравнить расчёт по небольшой известной выборке с обеими визуализациями.
- Проверить время расчёта, кеш, ошибки записи и отсутствие дополнительного ожидания Redis/полного сканирования на пути голосового ответа. Локальные тесты не доказывают приёмку PROD.
