# Дашборд практических звонков Telegram

Статус: реализовано локально; DEV/PROD и реальные Telegram-сценарии не проверены. Текущий контракт и ограничения — в [интеграции](../integrations/2026-10-05-telegram-call-dashboard.md). Основание: согласованный набор метрик в обсуждении 2026-10-05. Сценарий звонка описан в [Telegram practice calls](../integrations/2026-09-30-telegram-calls.md); существующие голосовые исходы — в [voice error observability](../architecture/2026-10-05-voice-error-observability.md). Область охвата — Telegram practice calls после допуска к обычной практике. Онбординг и legacy-диалоги без открытого `callId` в показатели звонков не входят.

## Результат

Одна защищённая страница `/admin/metrics/calls` даёт сводку за сегодня, последние 7 или 30 московских дней и список звонков. Строка списка открывает `/admin/metrics/calls/{callId}` с хронологией одного звонка. Оба экрана читают одни и те же сохранённые факты. Пользовательский сценарий Telegram, содержание реплик и модельные вызовы не меняются.

## Определения и знаменатели

| Показатель | Определение |
| --- | --- |
| Звонок | Один `callId` из `CallStore`. Повторное нажатие `Start call` в активном звонке не создаёт второй звонок. |
| Начало кнопкой | Время получения допустимого текстового сообщения `🎙 Start call` в Ktor. Отдельно хранить время открытия звонка в AI-service и время доставки вступительного аудио. Недопустимые/неудачные нажатия видны как попытки старта, но не входят в число начатых звонков. |
| Начало голосовым | Время получения первого допустимого Telegram voice, приведшего к `calls/open`, и `callId`. Повторная доставка того же Telegram update не создаёт вторую запись. |
| Начало диалога | Время получения первого голосового пользователя в звонке. Для звонка только со вступительным аудио — «не начат». Задержка от кнопки до первого голоса считается только для начала кнопкой. |
| Конец диалога | Время доставки ответа на последнее голосовое, если он доставлен. Если последнее голосовое осталось без ответа, время его получения с явной пометкой «ответ не доставлен». Это не время закрытия звонка. |
| Закрытие звонка | Время фактического `seal` и причина: `end_button`, `next_moscow_day`, `onboarding_reset` или иная явно классифицированная причина. Звонок без `seal` остаётся открытым, даже если пользователь давно молчит. Закрытие при следующем обращении после полуночи обозначается как отложенное, а не как событие ровно в 00:00. |
| Длительности | Три независимые величины: интервал открытого звонка; сумма длительностей файлов по Telegram `VoiceContent.media.duration` (целые секунды, `null` при отсутствии); сумма распознанной речи из STT/CallStore. Тишина не добавляет распознанные секунды. Не подменять одно поле другим. |
| Голосовые | Каждое допустимое полученное сообщение `(chat_id, message_id)`, включая тишину и неудачную обработку. На деталях показывать время получения, длину файла, распознанные секунды, исход и связанный `attempt_id`. Недопущенные голоса из онбординга/гейта не входят в звонок. |
| Ответы бота | Число основных аудиоответов, принятых Telegram. Вступительное аудио после кнопки считать отдельно. Успешный текстовый fallback показывать отдельно, не выдавая его за аудиоответ. Для каждой попытки голоса показывать один исход ответа или «ожидается/неизвестно». |
| Ожидание ответа | Монотонный интервал от получения голоса вебхуком до принятия основного аудио Telegram. Включает ожидание очередей и обработку. Для текстового fallback — такое же время до текста с отдельной меткой; для неудачи — время до терминального исхода, не смешивать с задержками доставленных аудио. Выводить каждое время, p50/p95 и размер выборки. |
| Исправления | «Сформировано» = принятая проверкой модельная коррекция для данного хода; «к отправке» = выбранная карточка (сейчас максимум одна в practice call); «доставлено» = Telegram принял карточку. Разница между количеством принятых коррекций и карточек отображается явно. Повторный webhook/Retry не прибавляет карточку. |
| Subtitles | Все полученные нажатия, число уникальных Telegram message ID ответов бота, для которых нажали кнопку, и число повторных нажатий. Отдельно считать успешный показ текста и нажатие без доступного текста после перезапуска или старого сообщения. Нажатие не доказывает прочтение. Вступительное аудио допускается как отдельный тип ответа. |
| Review | Время запроса итога, исход генерации и время принятия итоговой карточки Telegram; Retry может доставить review позже. «Сгенерирован» и «доставлен» — разные состояния. |
| Цель | Снимок выбранной цели при открытии: 5/10/15 минут или явное `No goal for now` (0). Показывать распознанные секунды звонка и, отдельно, прогресс за московский день с учётом других звонков. Факт достижения цели считается только при положительной цели. |

Период и дневные строки выбираются по московской дате начала звонка. Открытые звонки показываются отдельно; показатели завершения и длительности закрытого звонка используют только закрытые звонки. Счётчики сообщений показывают число событий и число звонков, где они встречались. Не вычислять среднее из дневных p95. Фильтры: период, способ начала, состояние закрытия, наличие неудачного ответа. Список сортируется по началу, с ограниченной пагинацией. Для низких выборок показывать `n`, а для неизвестных/неполных данных — `—`, не ноль.

## Факты и корреляция

`CallStore` в AI-service/Redis остаётся источником состояния звонка и распознанных секунд. Ktor/Postgres хранит долговременные факты дашборда, потому что только Ktor знает Telegram update, callback, отправленные сообщения и итог доставки. Новый Flyway `V9` (следующий после текущего V8) вводит компактные таблицы для звонка, попыток старта, голосовых ходов, ответов/карточек и нажатий Subtitles. Ключи:

- `call_id` связывает все записи звонка; `(chat_id, message_id)` или существующий `attempt_id` однозначно определяет голосовое. Для вступительного и обычного аудио хранить Telegram `bot_message_id`, чтобы привязать Subtitles к конкретному ответу.
- Для `Start call` использовать `(chat_id, incoming_message_id)`; для `End call` и Subtitles — Telegram callback query ID. Для карточек и ответов — стабильный ID исходной операции плюс полученный `bot_message_id`. Уникальные ограничения делают повторную доставку webhook и повторную запись безопасными.
- Сохранять `received_at`, `pressed_at`, `delivered_at`, `closed_at` как `timestamptz`, миллисекунды ожидания — из монотонных часов Ktor. В ответах внутренних API передавать только ограниченные структурированные факты: `callId`, фактические времена/причину открытия и закрытия, распознанные секунды хода, состояние review. Не переносить транскрипты, исправленные фразы или аудио в Postgres.
- Не расширять единственную терминальную запись `telegram_voice_attempts` для поздних карточек/кликов: её текущий store игнорирует обновления после исхода. Использовать отдельные таблицы/идемпотентные операции и связать их с существующим `attempt_id` для перехода к диагностике ошибок.

План сбора по пути пользователя:

1. На допустимом `Start call` записать получение кнопки до генерации вступления; затем связать попытку с `callId`, зафиксировать открытие и исход доставки starter. Если AI создал открытый звонок, а генерация или Telegram-отправка завершилась ошибкой, попытка остаётся видимой; следующее успешное обращение к тому же `callId` дополняет запись. Для начала голосовым записать `callId` сразу после `calls/open`, до постановки клипа в очередь, чтобы не терять неудачные голоса.
2. Передать длительность Telegram voice как nullable факт при приёме. После STT добавить в контракт клипа распознанные секунды конкретного хода; не выводить их из разницы дневных сумм. Привязать финальный исход существующего `VoiceAttemptRecorder` к ходу, включая очередь, ошибку, текстовый fallback и неизвестный исход.
3. На каждом принятом Telegram основном ответе сохранить `bot_message_id`, время и полное ожидание от получения голоса. На ошибке сохранить терминальный исход и время; не создавать фиктивную доставку. В момент выбора и отправки коррекции зафиксировать отдельные `accepted`, `selected`, `delivered/failed`, потому что карточка отправляется раньше основного аудио и её успех не означает успех аудио.
4. Для Subtitles сохранять callback с `bot_message_id` и результатом показа. Нужна долговременная привязка bot message → `callId`, поскольку текущий `spokenLines` живёт только в памяти процесса. Не сохранять сам текст ради аналитики и не менять поведение старых кнопок в этой задаче.
5. На `End call` записать время нажатия до ожидания очереди, затем фактическое закрытие и причину. Для закрытия на следующий московский день или через `/onboarding` AI должен возвращать/передавать достаточно метаданных, чтобы Ktor записал закрытие прежнего `callId`. Генерацию review и принятие карточки записывать отдельно, включая последующий Retry.

Записи аналитики не должны блокировать доставку или следующее действие в `TelegramChatActions`. Использовать ограниченный асинхронный recorder с контролем переполнения, ошибок и коротким drain при остановке, по аналогии с `VoiceAttemptRecorder`; проверить порядок и поздние обновления. Сбои сбора данных показывать на странице как неполноту, а не как нулевую активность. Для 30-дневного окна задать 30 дней хранения детальных записей и очистку небольшими пакетами. Историю до включения инструментации не восстанавливать из неполных Redis/логов; страница показывает дату первого наблюдения.

## Экраны

**Сводка:** число начатых звонков и попыток кнопки, способы начала, открытые/закрытые по причинам, доля начавших диалог, время до первого голоса, количество/длительности голосовых, число аудиоответов и fallback, ожидание p50/p95 с `n`, сформированные/доставленные исправления, нажатия/уникальные открытия Subtitles, доставка review и прогресс к цели. Под сводкой — ограниченная таблица последних звонков: время, Telegram chat ID/безопасный username для админского разбора, `callId`, способ начала, состояние, голоса, речевые минуты, ответы и сбои. Агрегаты и список используют одинаковый фильтр.

**Детали:** отметки получения кнопки, открытия и starter; начало/конец диалога; каждый голос с длительностью файла и речи, исходом и связанным ответом; ожидание ответа; исправления и Subtitles для конкретного ответа; нажатие End, фактическое закрытие, review. Наверху — три длительности и цель. Показывать причины пропусков и неполноты; не выводить транскрипты, аудио и текст ответов.

Оба маршрута используют существующую `METRICS_PASSWORD`/cookie-сессию и вкладку админки, `Cache-Control: no-store`, HTML-экранирование и ограниченные параметры. На странице ошибок оставить прежние значения метрик; деталь звонка может ссылаться на существующий `attempt_id`. Для локального режима без `DATABASE_URL` — ограниченное хранилище в памяти с явной меткой «данные пропадут при перезапуске».

## Порядок реализации и проверка

1. Зафиксировать DTO и схему V9, memory/Postgres store и идемпотентный recorder. Сначала проверить Flyway на существующей базе и уникальные ключи, поздние события, очистку и сбой записи.
2. Инструментировать открытие/закрытие в AI и Ktor, включая неудачную генерацию starter, прямое голосовое, повторный `Start call`, `End call`, отложенное закрытие на следующий день и `/onboarding`.
3. Связать голосовые с `callId`, Telegram duration, распознанными секундами, `VoiceAttempt` и доставкой каждого ответа. Проверить тишину, очередь, STT/TTS/Telegram-сбой и текстовый fallback.
4. Добавить факты исправлений, Subtitles и review, включая повторный callback, Retry, рестарт Ktor и ошибку необязательной карточки.
5. Построить агрегаты и список из ограниченных индексированных запросов; затем страницу деталей. Проверить совпадение итогов списка и сводки, московскую полночь, пустые/неполные данные, HTML-экранирование, авторизацию и пагинацию.
6. Запустить Python-тесты звонков/пайплайна и `:server:test` из `cmp/` с `GRADLE_USER_HOME=$HOME/.gradle`; интеграционные тесты Flyway/JDBC на временном Postgres; `git diff --check`. На близком к ожидаемому объёме проверить `EXPLAIN (ANALYZE, BUFFERS)`, время страницы и p50/p95/p99 доставки ответа/ожидания очереди до и после инструментирования. На DEV вручную сверить реальные Telegram-события с одной карточкой звонка и общими числами. Выкладка и проверка PROD — отдельные действия.

Критерий готовности: любой наблюдаемый звонок имеет один `callId`, корректный способ начала и исход; каждый допустимый голос имеет один связанный ход и не более одного основного терминального исхода; успешная доставка считается только после принятия Telegram; суммы деталей согласуются со сводкой; открытые звонки и пропущенные записи видны как отдельные состояния; сбор аналитики не меняет ответ пользователю.
