# План: история взаимодействий и логи сервисов

Status: implementation in progress in the repository. The [agreed architecture](../architecture/2026-10-05-conversation-audit-logging.md) records current code and remaining release checks. The implementation covers the Telegram bot first. Deployment is a separate action.

## Result and definitions

- At the existing Grafana address, every authenticated Grafana user can open **История** and **Логи сервисов**. History is searchable by Telegram chat ID, date, `attempt_id`, and job ID. A chat timeline shows incoming commands/text/buttons/voice, onboarding and call steps, STT text, generated reply, Telegram messages actually accepted, failed attempts, and retries. A link opens Grafana logs for the same `attempt_id` and time window.
- **Generated** means AI produced text/audio. **Sent** means Telegram API accepted a specific outgoing message and returned its message ID. It does not mean read or listened to. Failed/uncertain sends remain attempts, never successful deliveries.
- Incoming voice bytes, user text/STT transcript, and generated/outgoing text are content. Retain them for **7 × 24 hours from receipt**; apply the same deadline to every copy, including existing Redis state. Outgoing synthesized audio is not archived.
- Keep interaction metadata and outcomes for 30 days. Proposed operational Loki retention is also 30 days, subject to DEV disk sizing; if measured volume makes this impractical, revise the log period explicitly before PROD rather than silently filling the disk. No earlier interactions can be reliably backfilled.

## Design choices to implement

### 1. Storage and correlation

- Keep the authoritative interaction timeline in **CMP-host Postgres**. Add a Flyway migration with `interaction_events` (stable event ID, chat ID, Telegram update/message ID, direction, bounded event type/status, `attempt_id`, job ID, occurred/recorded times, optional call/onboarding IDs, fixed error code) and a separate restricted content table keyed by event/attempt. Make event IDs unique and writes idempotent. Index `(chat_id, occurred_at DESC)` and `attempt_id`; page queries must be date-bounded and cursor-paginated. Reuse `telegram_voice_attempts` by reference rather than duplicating its outcome/timing columns.
- For seven-day voice storage, use a **private host-mounted directory on the CMP VPS** for the first deployment: Ktor already downloads each Telegram voice there, and the same host owns Postgres and the operator page. Add a persistent Docker mount outside the image; write to a temporary file, atomically rename, use an opaque `attempt_id` filename, store MIME/size/hash/reference in Postgres, and expose bytes only through an authenticated, range-capable playback endpoint. No Telegram file URL, object path, or token appears in HTML. Check measured volume, free-space headroom and backup behavior before enabling capture; later migration to private object storage must preserve the same content/expiry contract.
- Stamp every event with UTC time and use one deadline derived from original receipt. Carry `attempt_id` through Ktor, clip form, AI job and logs. Use separate stable IDs for non-voice updates and for each outgoing send attempt; deduplicate webhook redelivery while preserving genuine retries. Never use chat/user/request IDs as Loki labels.
- Restrict text length and audio size to explicit limits based on current Telegram/clip limits; reject or mark oversized archival content without changing the existing bot reply path. Store exact displayed text/entities in the content table where needed to reconstruct an outbound card, not raw webhook/provider payloads or credentials.

### 2. Capture the complete interaction

- Add one shared Ktor outbound Telegram adapter so command handlers, optional correction cards, call openings/reviews, reminders and campaign messages all record `send_attempted`, `send_accepted(message_id)` or `send_failed`. Handle edits, reactions and callback answers as separate event kinds; record callback action/state transitions after acceptance. Audit each handler path to ensure it uses the adapter, including fallback text. Do not create extra chat messages just for logging.
- Persist an inbound envelope synchronously and idempotently before webhook HTTP 200. On a database failure, return a retryable 5xx and avoid dispatching that update; bound the database call so a stalled audit store cannot hang webhook workers. Continue processing asynchronously only after receipt is durable. Verify how the Telegram library dispatches and acknowledges the update before modifying this boundary. For downstream operations, use a bounded writer with retries and visible write-loss/pending counters, or a Postgres outbox when an event must be durable with a state transition. Never claim full history if a crash gap remains.
- Store incoming audio immediately after a successful Telegram download and before AI submission. A failed download still gets metadata and an explicit `audio_unavailable` reason. Onboarding technical Retry links to the original voice rather than creating another user-received event.
- At the AI STT boundary, record transcript availability **before** later LLM/TTS work. Store short-lived stage artifacts by `attempt_id` on the AI host with the original absolute expiry; expose them through a token-protected internal read endpoint. Ktor imports them into Postgres during job polling and reconciles unfinished attempts after restart. A failed or crashed AI job must show the last known stage even when no final reply exists. Reconcile idempotently; distinguish missing artifact from empty/no-speech STT. The present Redis container uses periodic RDB snapshots, so an AI-host crash can still lose recent stage artifacts; measure/report that gap rather than promise exactly-once capture.
- Record generated reply text separately from outbound Telegram voice/text acceptance. For ordinary replies, the current clip result already contains transcript and `replyText`; include onboarding, clarification, call starter/closing and text fallback paths. Follow-up cards and explicit user actions each get their own event. Keep raw provider prompts/responses, API keys, entire Telegram update JSON and output voice bytes out of the audit.

### 3. Seven-day expiry across all copies

- Give new dialogue messages and onboarding/call turns per-turn UTC timestamps. Reads and writes filter expired content; a sweeper rewrites existing Redis keys to remove expired `transcript`, `reply`, question/closing text, word tokens, correction snippets and any other raw excerpts while retaining required state and derived learner facts. Audit stored review payloads/exemplars for exact user quotes and treat those quotes as seven-day content. Test resume/retry, call review and personalization after pruning.
- **Legacy rows lack per-turn time.** Do not infer age from refreshed Redis TTL. On rollout, inventory affected key counts and create an explicit one-time migration that drops untime-stamped raw turns/quotes while preserving assessment/status/goal/profile fields; document the expected loss of old conversational context. Ensure `/start` or the next voice does not copy legacy text back into new state.
- Run bounded Postgres content/file cleanup and Redis cleanup on a schedule. Content reads check `now < receipt + 7 days` before returning bytes/text, even if cleanup is delayed. Delete orphan files and prevent path traversal. Retain event metadata 30 days, then prune in bounded batches. Monitor cleanup lag, bytes/files, disk free space and failed deletes. Check snapshot/backup retention and restore procedures so expired content is not reintroduced by backup restoration.

### 4. Operator UI and access

- Add Ktor history list/detail/audio endpoints on the localhost `MONITORING_PORT`; prohibit the public TLS connector from serving them directly. Extend the current Nginx Grafana-session check to **every** history/API/audio path. Verify logged-out, expired-cookie and logged-in requests against both connectors, including `Range` requests; no query parameter or forwarded header may bypass authentication. Existing shared Grafana admin login grants everyone with Grafana access the same history access; individual view attribution is unavailable with a shared account.
- Build a compact timeline page with filters, timestamps, stage/outcome badges, text and audio for unexpired records, and explicit `expired`, `not captured`, `write failed`, and `not yet processed` states. Escape user/model text as data. Link an attempt to a time-bounded Grafana Explore query; do not embed audio or transcript in the URL.
- Keep the existing `/admin/metrics/errors` and `/admin/monitoring/errors` semantics intact. Their attempt/result counts can link into history; a missing source must render unavailable rather than zero.

### 5. Container logs

- Provision Loki on the CMP monitoring host with a persistent volume, localhost-only API and Grafana data source. Install Alloy on **both** hosts, collecting Docker stdout/stderr through Docker discovery/API and labeling only environment, host and service. Send AI-host logs to Loki over authenticated TLS/private transport; do not expose an unauthenticated Loki write port to the internet or mount the Docker socket into the history UI. Collect Ktor stdout once (it also writes `app.log`) to avoid duplicate entries.
- Standardize bounded structured correlation fields (`attempt_id`, `job_id`, service, stage, severity), redact tokens and personal text, and keep transcript/audio out of logs. Retain `docker logs` locally with rotation, independently of Loki availability. Configure Loki compactor retention, persistent state and disk alarms. Prove that Alloy/Loki failure does not stall either service and that logs from both VPS hosts appear in Grafana.

## Sequence and gates

1. **Contract and sizing:** enumerate inbound/outbound Telegram entry points and raw-content copies; measure DEV/PROD voice counts, representative OGG sizes and log volume without downloading user content. Set file/text limits, disk budget, index/query bounds and cleanup cadence. Agree the exact event enum and migration behavior before code changes.
2. **Data foundation:** Flyway tables, private audio volume, store/repository, deterministic IDs, expiry-aware reads and deletion worker. Verify idempotency, atomic file writes, orphan cleanup and `7 days - 1 second` / `7 days` boundaries with controlled fixtures.
3. **Capture:** webhook receipt gate, shared send adapter, voice download, AI stage artifacts and reconciliation; preserve old AI/Ktor DTO behavior across deploy order. Test duplicate webhook updates, both queue-full paths, no-speech, successful voice, text fallback, Telegram send failure, onboarding Retry, commands, callbacks, reminders and call lifecycle.
4. **Existing-state cleanup:** timestamp new turns, remove legacy raw content once, prune all Redis/review copies, and verify onboarding/call continuation and derived personalization. Re-scan Redis data shapes for remaining original excerpts before considering expiry complete.
5. **UI and auth:** history pages/endpoints, Grafana gate and links to errors/logs. Test authorization on HTML, JSON and audio, pagination, escaping, expiry and missing sources.
6. **Loki/Alloy:** add both-host collectors and Grafana data source; load-test disk/retention, redaction and correlation. Check no public ingestion endpoint and no duplicate Ktor log stream.
7. **Release:** run Python tests from `ai-service/` with Python 3.12 and `./gradlew :server:test` from `cmp/`, Flyway/Postgres integration checks, script syntax/config checks and `git diff --check`. On DEV, compare before/after p50/p95/p99 reply latency and queue wait, reconcile a known set of Telegram events against history, then check seven-day expiry with a controlled old fixture and both-host log search. Require a separate PROD deploy decision after DEV results; watch audit write failures, cleanup lag, disk and login failures after rollout. No historical backfill is promised.

Acceptance: every accepted Telegram update has one durable inbound envelope; every outgoing API attempt has a visible accepted/failed/uncertain outcome; each processed voice links receipt, audio when downloaded, STT when available, generated text, Telegram delivery and service logs by stable identifiers; all raw content becomes inaccessible at seven days and is cleaned from every identified store; metadata and container logs obey bounded retention; the bot's normal delivery and existing metrics remain correct. Any unavoidable crash-loss window is measured and shown as an observability gap, not presented as a complete record.
