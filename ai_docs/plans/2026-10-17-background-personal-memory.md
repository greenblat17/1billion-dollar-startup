# Background personal-memory updates

Status: implemented locally; real-provider structured-output acceptance, live Telegram acceptance, and deployment pending. Scope: ordinary voice turns only. Preserve onboarding seeding, continuation behavior, scenario exclusion, profile field limits, and the existing seven-day retention rule for raw transcripts.

## Current path and goal

`ClipPipeline._run_bound` starts `Personalization.extract_person` alongside notes and reply generation, then awaits it and `save_observation` after TTS. Extraction has a five-second limit. A slow memory call can therefore delay a completed voice clip. `_update_person` catches all model failures and returns the old profile, so callers cannot distinguish a successful no-change extraction from a failed one or retry it. `OnboardingModel.update_person` requests JSON object mode and validates locally, but reports only broad `ValueError` messages. The existing `main.py` task set and in-memory clip jobs are process-local and are not a recovery mechanism for memory work.

The voice result must stop waiting for extraction. A successful ordinary turn must enqueue a recoverable memory job after the pipeline has finished reply audio and finalization, before the clip job is marked complete; a failed, cancelled, clarification, load-test, or scenario turn must not enqueue one. Continue to update `lastConversationAt` after a successful turn independently of fact extraction so return greetings remain correct. Keep this lightweight state update and enqueue bounded; if Redis is unavailable, the voice result still completes and an `enqueue_failed` signal is recorded. Do not claim that a failed enqueue is recoverable.

## Immediate conversation versus lasting memory

The current reply sees the current transcript directly. After an ordinary turn, `DialogueStore.record_turn` saves both the user's words and the bot's answer in the rolling session history. The next ordinary reply reads that history before generating text, so it must be able to use a just-mentioned move to Kazan even while the background memory job is pending. Test this with a deliberately blocked memory worker and two consecutive turns. History is bounded to 40 messages and raw turns are kept for at most seven days; it is context for the current conversation, not the lasting-memory guarantee.

The model chooses candidate lasting facts from the user's transcript and the current `person` record. Instructions allow only explicitly stated, durable details (name, work, leisure, English goal, up to 12 short facts), replace contradictions, honor requests to forget, and exclude guesses or sensitive inferences. Strict JSON schema and local validation protect shape and size; they do not prove the model understood the fact correctly. Add a real-model acceptance case for “I moved to Kazan” and a contradiction/forget case. After successful extraction the fact goes into `learner:{sessionId}` without TTL and is read for later ordinary conversations by that same session. For Telegram, the session ID is derived from the chat ID and remains stable across calls/days. Cross-platform identity sharing is outside this plan; a mobile session with a different ID does not automatically share Telegram memory.

## Job contract and storage

- Add a dedicated Redis-backed memory-job store and in-memory equivalent for tests. Each job contains an opaque ID (Telegram `attemptId` when present, otherwise clip job ID), session ID, the user's transcript, creation time, attempt count, and status. A validated candidate person object is stored only if saving fails, so a save retry does not call the model again. Do not include assistant text or the proficiency/assessment snapshot. Use the same seven-day maximum lifetime as other raw conversation content and delete the payload after success or final failure.
- Enqueue idempotently: the same voice attempt must not create another job. Persist the job before reporting the clip complete. Record enqueue duration and failure separately from extraction duration; use a short bounded Redis operation so queue trouble does not hold the voice result for seconds.
- Process different sessions concurrently with a small fixed worker limit. For each session, claim only the head of its FIFO queue under a lease; acknowledge/remove it only after the profile update is committed or a terminal failure is recorded. On startup and after lease expiry, reclaim unfinished jobs. Do not rely on a detached `asyncio.create_task` alone: it does not survive a process restart.
- Make profile application idempotent. A worker restart between profile save and queue acknowledgement must not apply the same job twice. Use an applied job marker with the learner record and a compare-and-set/transactional write. Read the current learner profile when processing the job. Preserve assessment/proficiency fields and re-extract from newer person facts if an assessment or another writer changes them while the model is running. Keep the existing per-session lock for local callers; the Redis write rule must also cover worker/restart races.

## Deadline, retry, and schema

- Interpret **20 seconds as the total wall-clock budget for extraction**, including at most two model calls, validation, and a short backoff. Give the first call at most about 12 seconds and the second the remaining budget. Never let either call inherit the voice pipeline's 60-second deadline. On a transient provider failure or timeout, retry once; on invalid model output, retry once with the same schema. If the 20-second extraction budget expires, leave existing facts intact and mark the job terminal `timeout`. Bound the Redis save separately to a short operation. If saving fails after a valid extraction, retry that save through the queue with a bounded attempt count and backoff, without calling the model again.
- Request a strict `json_schema` response for the existing `person` object (four nullable strings and a required `facts` array). Confirm the configured OpenRouter model/provider accepts this format before release. Keep local validation as the final gate: required keys, types, 12-fact limit, 240-character string limit, nonempty facts, and the existing deduplication. Reject invalid output rather than truncating or silently saving it.
- Replace broad validation errors with fixed reason codes such as `person_missing`, `field_missing`, `field_type`, `field_too_long`, `facts_missing`, `facts_type`, `facts_too_many`, `facts_empty`, and `facts_too_long`. Keep `provider_timeout`, `provider_error`, `enqueue_failed`, `save_failed`, and `retry_exhausted` distinct. Do not log or label transcript, profile values, raw model output, or exception strings that might contain personal data.

## Metrics and operations

- Count queued, started, succeeded, retried, terminal failed, and enqueue failed jobs. Add fixed reason counters and queue age/pending depth; tie diagnostic logs to opaque job ID and session hash rather than transcript or facts. Show final outcome separately from per-attempt errors, so a recovered retry does not count as a lost memory update.
- Preserve the current learner record without TTL; expire only queued raw transcript payloads. Report expired/dead jobs explicitly. During shutdown stop claiming new work and let active leases expire or finish within a bounded grace period. The worker must restart automatically with the AI service.
- Update `ai_docs/integrations/2026-09-30-personalized-conversation.md` and the relevant monitoring contract after implementation to reflect eventual consistency: an immediately following voice turn may read the previous fact set while a job is pending.
