# Stage-specific Telegram onboarding follow-ups

Status: implemented locally on `feature/onboarding-nudge-analytics`; automated checks passed, live DEV Telegram acceptance and deployment remain outstanding. This extends [the personalized send-time plan](2026-10-20-personal-onboarding-nudge-time.md). The previous bot had only three fixed texts and stopped nudging at result delivery. The journey dashboard's 16 stages are defined by `JOURNEY_STAGES` in `OnboardingJourney.kt`; analytics stages describe observed milestones, not necessarily a safe next action.

## Product rules

- Prepare 10 concise A2-English reminder variants for **each of the 16 journey stages**, including stages after result delivery. Variants within a stage should share the same truthful next action but vary phrasing, not just emoji. No generated-at-send-time LLM call. Copy is a reviewed, versioned catalog in source control.
- Select the deepest verified stage of the latest relevant attempt immediately before sending. A stage is reached only from its durable milestone, not because the dashboard inferred that the user ought to be there. A live AI-service state check remains mandatory; technical failures, restarted attempts and stale callbacks must select a valid recovery action or skip sending. Never tell a user their result is ready before `result_delivered_at`.
- A visit without stage progress does not reset the stage's budget. Try each variant at most once per user per stage, in a deterministic shuffled order. A Telegram-accepted send consumes its variant slot. An uncertain outcome may have been delivered, so quarantine that variant and consume its slot too; a definite failure consumes the day's claim but its variant may be tried again later. Persist stage ID, copy ID, catalog version and outcome in the send ledger. A different stage starts its own budget. Do not reuse an earlier stage's budget if an attempt is restarted; final suppression and user opt-out persist across attempts.
- After all 10 variant slots in a stage have been consumed, schedule **one final message** at the next personalized daily slot if the stage has not advanced and at least one send was confirmed accepted. Normally this follows 10 accepted reminders; uncertain sends can make the confirmed count lower. Suggested English copy: “I don't want to send too many check-ins, so I'll stop these for now. You can come back whenever you're ready.” Record that final message separately, then stop this follow-up sequence for that stage. No eleventh reminder and no further cycle. If the user advances, the new stage may have its own 10 variants; the existing `Not now` choice ends the whole sequence.
- Keep the **one-time reminder question in the onboarding flow** after the goal choice, with its existing `Set reminder` and `Not now` buttons. Do not use `goal_decided` or `reminder_offered` follow-ups to ask for that choice again. Once the goal is chosen, later follow-ups invite the user to have a practice conversation with Speaky and provide `Start call`, even if the reminder question is still unanswered. The ordinary goal message already offers `Start call`; remove only the repeated reminder-choice call to action from follow-up copy.
- After `result_delivered`, invite the user to open and review the result, then choose a practice goal. Once the goal is selected, the [ongoing practice reminder rules](2026-10-20-ongoing-practice-reminders.md) replace the older per-stage stopping rule: 14 sends plus a final note without a saved reminder time; ongoing daily reminders at the chosen time when one is saved. The first ordinary practice call does not end either path. The explicit `Not now` decision suppresses automatic sends. Never send two daily messages for the same purpose.
- Every follow-up, including the final note and one sent at the opted-in `/remind` time, has a next-step button. Do not include `Stop these messages`: the user explicitly rejected it. The existing onboarding `Not now` still suppresses this sequence durably and cancels a queued final note; Telegram 403 blocks remain honored. It does not change the separately opted-in `/remind` schedule.
- In an active onboarding conversation, `Continue 🎙` copies the most recently delivered Speaky voice question from the current attempt. Persist that Telegram message ID when delivery succeeds. The button must not create a new AI turn or restart the first question. Recheck the current attempt and stage when an older button is pressed, and offer the current step if it has changed. For attempts without a saved voice ID, give safe guidance rather than generating a new question.
- Use the existing one-per-Moscow-day durable claim and the personalized time, 24-hour inbound inactivity condition and two-hour catch-up window. An inbound response postpones the next message, even when it does not advance a stage. The final note is another day's message, never appended immediately after reminder number 10.

## Stage-to-action map for catalog review

| Journey stage | Safe next action for copy and keyboard |
| --- | --- |
| `start` | Retry or deliver the invitation only if the chat and attempt are valid; if delivery is uncertain, skip. |
| `invitation` | Tap Let’s chat. |
| `begin` | Recover or deliver the first question; do not ask for a voice before the question is visible. |
| `first_question`, `voice_received` | Copy the last delivered Speaky voice question if the AI-service state is active; do not generate a new question while a user reply is being processed. If the state is pending, offer Retry instead. |
| `voice_recognized`, `speech_30`, `speech_60`, `speech_90`, `speech_120` | Copy the last delivered Speaky voice question so the user can continue answering; avoid claiming the next milestone is already reached. |
| `result_delivered` | Open the result with the existing button. |
| `result_opened` | Continue through the review with a valid review button. |
| `goal_shown` | Choose or skip a daily-minute goal. |
| `goal_decided` | Invite a practice conversation with Speaky using `Start call`; the one-time reminder question remains available separately. |
| `reminder_offered` | Invite a practice conversation with `Start call`, **not** another request to set a reminder. The existing `Not now` button remains available on the onboarding question. |
| `reminder_resolved` | Invite a practice conversation, unless the user chose `Not now` or already completed a practice call; coalesce with active `/remind`. |

The `pending` technical state still needs its own 10 retry-safe variants because the next valid action can differ from the deepest analytics stage. Do not send a stage variant when its mapped button/action cannot be reconstructed safely. Before implementation, review all catalog entries against current English UI copy and Telegram callback behavior; keep each line short and avoid promised levels, scores, or recovery outcomes.

The 16-by-10 English catalog and 10 retry variants are bundled as `onboarding-followup-copy.tsv`; the draft source is [the product copy document](../product/2026-10-20-onboarding-followup-copy.md). `FollowupStore.kt` persists stage and copy IDs, enforces the stage budget, remembers the last delivered bot voice per attempt, and pauses a completed stage until it advances. `FollowupKeyboard.kt` supplies next-step buttons, including on the final note. The dashboard JSON uses `onboarding-nudges.v2` and keeps legacy sends distinct. Deployment still needs separate authorization.
