## 1. Цель и результат

Зафиксировать один проверяемый контракт материала для четырёх Teaching Methods: Explanation,
Exercises, Exposure и Conversation. Конкретный материал всегда следует выбранной Learning Task,
исторической версии Plan/Stage, формату конкретного задания, каталогу и учебной цели. Контракт
должен передать SP-13B входы генерации и проверки, а уроку — исполнимый голосом материал и
смысловые ориентиры для AI-репетитора. Ошибка в условии не должна стать ошибкой ученика.

Простыми словами: метод — «упражнение», «разговор», «объяснение» или «аудирование».
Конкретное действие — например, попросить изменить короткую фразу в прошедшее время.
Контент — сама фраза, понятное условие и признаки удачного ответа. Ни метод, ни «контент сервис»
не принимают решения. AI-репетитор слушает реальный ответ и решает, верен ли он по смыслу.

Результат SP-13A: схема и валидатор контракта, примеры для всех четырёх методов и основных
исключений, документированный жизненный цикл и проверенные границы с SP-12B/SP-13B/SP-17C.
Наличие формы не означает готовый генератор, голосовое исполнение или живую проверку ответов.

## 3. Владение и границы

| Компонент | Решение и выход |
| --- | --- |
| SP-12B | Выбор методов, порядка, весов, Stage и педагогического перехода. |
| SP-13A | Форма входов/выходов, идентичность, версии, качество и жизненный цикл Content. |
| SP-13B | Реальная генерация, семантическая проверка материала, озвучиваемость и регенерация по контракту. |
| SP-14/15 | AI-репетитор проводит объяснение, упражнение, аудирование или разговор; принимает решение по реальному ответу и даёт обратную связь. |
| SP-17C | Доказательное Observation из Action outcome; дефектный Content исключает штраф и scoring. |
| SP-19 | Stage Score и Task Progress по пригодным Observations. |

Граница двух разных работ: SP-13A описывает **какой ответ допускает данное задание**
(например, какие формулировки передают нужный смысл). Это свойство подготовленного материала.
AI-репетитор во время SP-14/15 слушает **фактический ответ ученика**, решает, подходит ли он,
и отвечает ученику. SP-13A не реализует проверку пользовательских ответов. Notion SP-13A
называет выход «критерии смысловой корректности» и требует альтернативы; родительская SP-13
одновременно закрепляет AC-09: отдельная оценка ученика здесь не реализуется.

SP-13A не выбирает Plan или педагогические веса, не исполняет Voice Action, не извлекает
Observations, не ставит CEFR и не считает Score. Trial extractor SP-17B не зависит от Content.
Нет нового UI, Homework video library, изменений legacy lesson plan или автоматического
подключения к текущему regular lesson runtime.

Handoff SP-12B через родителя: его отдельный педагогический planner в `ai-service` получает
Task + catalog + learner context и создаёт состав/этапы через существующий SP-12A
FoundationClient create/revise/select. Он не меняет Kotlin schema или Flyway. SP-13A принимает
его исторический StageRef и выбранный метод; форма Content и Action остаётся у SP-13A.
После интервью SP-12B выбирает Plan только из заданных шаблонов с заранее заданными весами.
Состав/веса сохранённого Plan меняются только между уроками. Content не меняет метод, Stage,
веса или Plan; при отсутствии шаблона не создаёт обходную LLM-комбинацию. Обработка отсутствующего
шаблона остаётся открытым решением SP-12B, а Content возвращает явное отсутствие валидного входа.
Шесть предложенных MVP-шаблонов SP-12B: Grammar unknown = Explanation(binary) +
Exercises(30%) + Conversation(70%); Grammar application = Exercises(30%) + Conversation(70%);
Speaking = Conversation(100%); Listening = Exposure(100%); passive Vocabulary = Exercises(100%);
active Vocabulary = Exercises(30%) + Conversation(70%). План SP-12B ещё ожидает утверждения.
Все шесть укладываются в SP-12A и четыре метода Content. Для Listening reconstruction/meaning
входят в Action внутри Exposure Stage, а не требуют отдельного Exercises Stage. Имя формата
упражнения не определяет метод Stage. Для Speaking Conversation и passive Vocabulary Exercises
соответствующий payload работает без обязательных соседних методов.

## 4. Предлагаемый контракт

### 4.1. Вход подготовки

- `schemaVersion`; student берётся из проверенного execution scope, а не из произвольного JSON.
- `taskId` и текущая Task revision; актуальные `goalRevision`, `catalogVersion`, `skillId`,
  `topicId`, `problemId`, `objective/scope` читаются из Task и опубликованного каталога.
- Полный `stageRef={taskId,planId,planRevision,stageId}` разрешается по исторической Plan revision.
  `method` обязан совпасть с методом Stage. Для новой подготовки проверяется текущая связь Plan/Task;
  для чтения уже предъявленного материала сохраняется прежняя историческая ссылка. Смена шаблона
  Plan между уроками не перепривязывает ранее выданный Content к новой revision.
- `actionKind` задаёт конкретную форму внутри метода. `actionId` — отдельная identity исполнения,
  которую позднее определят SP-14/15; она не заменяет Content ID или Stage ID.
- Контекст сложности: текущий подтверждённый CEFR, self-report отдельно, допустимый Unknown,
  учебная цель, релевантные предпочтения и затруднения. Личные факты передаются минимумом,
  необходимым для материала; raw transcript не копируется в Plan или каталог.
- `requestReason`: first, simplify, rephrase, replace-defect, follow-up-question. Это основание
  подготовки, а не смена Roadmap или доказательство прогресса.

### 4.2. Общая оболочка выхода

- Устойчивая `contentId` и `revision`; `schemaVersion`, `createdAt`, технический `component`.
- Проверенные `taskId`, `stageRef`, `method`, `actionKind`, `catalogVersion`, Topic/Problem references.
- `spokenInstruction`/spoken segments: короткий текст, который можно произнести без экрана;
  отдельные приватные критерии оценки не озвучиваются как подсказка.
- `learningObjective`, условия ответа, `semanticRubric` (достаточные признаки правильного смысла,
  допустимые альтернативы, типичные недопустимые подмены, что остаётся неопределённым).
- `quality`: готовность к предъявлению, причины дефекта/неоднозначности/несоответствия уровню,
  provenance генерации и проверки. Флаг качества материала не является оценкой ученика.
- `parentContentRef` для упрощения, переформулировки или замены; прежняя версия остаётся
  связанной с ответом, который ученик услышал. Это инженерное правило для разбора урока,
  без дополнительного действия ученика.

### 4.3. Payload по методу

| Метод | Обязательный смысл payload |
| --- | --- |
| Explanation | direct/comparison/learner-example, тезис и короткие примеры, естественный вопрос или просьба привести пример для проверки понимания. «Понятно» само по себе не доказательство. |
| Exercises | Формат из voice-first библиотеки §16.2, короткое условие/stimulus, ожидаемая операция, смысловой rubric и альтернативы. Формат определяется выбранным Action, не самим валидатором. |
| Exposure | Короткие озвучиваемые фрагменты/диалог, порядок воспроизведения и повторения. В reconstruction ученик восстанавливает услышанную короткую фразу, а в meaning отдельно объясняет её смысл. Длинный текст и обязательный экран исключены. |
| Conversation | personalized/situational/topic-driven setup, мягкие prompts и возможности применить Topic/Problem; открытый ответ не имеет одного эталона. |

Action-specific данные используют tagged union по `method + actionKind`, без произвольного
непроверяемого поля. Набор Exercises из v5.5 содержит Sentence Construction/Transformation/
Correction, Translation, Word Recall, Meaning Recognition/Matching, Listening Reconstruction/
Comprehension, Rapid Response и Expansion/Paraphrasing. SP-13A фиксирует форму и инварианты;
какие форматы выбрать для конкретной Problem решает SP-12B/Action policy.
Listening Reconstruction/Comprehension также допустимы как шаги внутри Exposure payload:
их `method` остаётся Exposure, а `stageRef` — ссылкой на Exposure Stage. Это позволяет исполнить
Listening шаблон без скрытого добавления Exercises Stage или изменения его веса.

## 5. Жизненный цикл и ошибки

Предлагаемый путь: `prepared → validated → issued → superseded/defective`.
Fixture Content может пройти структурную проверку в SP-13A; готовность реального материала
подтверждает SP-13B. `issued` фиксирует утверждение trusted producer, что эту revision передали
в принадлежащий ученику regular Lesson. Сам контракт не подтверждает, что ученик её услышал;
это проверит SP-14/15. Запись `issued` не создаёт Observation. Текст/условие этой revision
не меняются задним числом.
Повтор предъявления использует ту же identity; исправление создаёт следующую revision того же
`contentId`. Другое независимое задание получает новый `contentId`. Показанная revision остаётся
неизменной, чтобы ответ ученика можно было связать именно с услышанным условием.

Если AI составил противоречивое условие или не учёл два правильных ответа, он принимает
допустимый ответ. Если условие нельзя честно оценить, Саша кратко уточняет или заменяет
задание без штрафа ученику. Технически SP-14/15 передаёт SP-17C `defective_content`
со ссылкой на событие; такая попытка не становится scoringEligible. Эту защиту требует
Notion SP-13A; она не является отдельным сценарием, который нужно предъявлять ученику.
Отказ ученика от Action — outcome исполнения, не дефект Content. SP-14/15 могут прекратить
Action и продолжить свободный разговор вне Task; отказ не двигает Stage и не меняет Score/Progress.
Content contract не вызывает `learning.plan.select-stage` по просьбе сменить Stage внутри Task:
такой переход не входит в текущий объём SP-12B. Свободный разговор вне Task не получает
фиктивный `taskId/stageRef` и не выдаётся за Content активной Task.
При техническом сбое или отсутствии надёжного материала возвращается явный отказ/новый запрос,
не придуманная ссылка или фиктивный успешный материал.

Смысловой rubric описывает задачу, а не конечный вердикт по неизвестному ответу.
AI-репетитор в уроке принимает допустимый неожиданный вариант; при неоднозначности
он уточняет ответ, а не наказывает ученика за несовпадение с примером.
Для короткого Listening reconstruction цель — восстановить услышанную фразу максимально
близко по словам, с разумными допусками к естественной речи и ошибкам распознавания.
Передача одного лишь общего смысла относится к отдельному шагу meaning и сама по себе
не означает успешное восстановление фразы. Числовой процент совпадения не вводится.

## 6. Идентичность, безопасность и данные

- Проверять student ownership Task/Plan/Stage; не доверять одним только строковым ID.
- Сохранять `catalogVersion` и исторический StageRef. Новая версия Plan не перенаправляет старый Content.
- Разделить Content ID, Action instance ID и Observation `attemptId`/`stageAttemptId`; ни один не
  создаётся на основе строки ответа ученика. Один показанный вариант может иметь несколько
  независимых попыток исполнения без копирования Stage.
- Явно определить idempotency/replay: повтор одного request/operation не создаёт иной материал;
  новая генерация получает новое основание/version. Точный storage protocol — после интервью.
- Ограничить длину spoken fields и segments, запретить обязательный экран/длинное чтение.
- Не писать raw audio, полный профиль, цитаты ученика или защищённые внешние фрагменты в
  бессрочный Content. Privacy/reset и retention должны соответствовать SP-03/04/17A.
- Старая `lesson_plan` и legacy content не backfill-ятся автоматически.

3. Реализовать чистую валидацию общих полей и tagged payload без вызова модели.
4. Если утверждено постоянное хранение: отдельные Content storage/read/write с ownership,

   SP-12B Plan selection и SP-17B Trial extraction.
6. Проверить handoff fixtures для SP-13B/14/15/17C и регрессию существующих контрактов.
7. Точечно обновить `ai_docs/README.md`, `ai_docs/status.md`, `architecture.md` и отдельный

## 8. Проверки и критерии приёмки

| Проверка | Ожидаемый результат |
| --- | --- |
| Четыре Teaching Methods и Action-specific fixtures | Один общий envelope; payload метода проверяется строго. |
| Task/Topic/Problem/CEFR/Action | Несовместимая ссылка или неверный scope отклоняется. Unknown CEFR не подменяется выдуманным уровнем. |
| Исторический StageRef и новая Plan revision | Контент остаётся связанным с предъявленным Stage; нет автоматического retargeting. |
| Голосовые задания и короткий Listening | Условие понятно без экрана; повтор/упрощение явно представлены. |
| Семантически верные альтернативы | Rubric допускает их; простое строковое несовпадение не означает ошибку. |
| Двусмысленность/дефект | Явный отдельный результат, без ошибки ученика и без scoring event. |
| Retry, revision и чужой student | Повтор детерминирован; чужие ссылки и мутация выданного материала отклоняются. |
| Privacy/reset | Нет восстановления удалённого контента или чужих данных; старый runtime сохраняет поведение. |
| Consumer handoff | SP-13B и SP-14/15 могут принять fixture; SP-17C получает точный defect signal. |

После реализации: Python `pytest` из `ai-service/`; Kotlin `:server:test :server:buildFatJar detekt`
из `cmp/`; при наличии storage — PostgreSQL и HTTP Python → Ktor → PostgreSQL; `git diff --check`.
Fixture/unit доказывают форму, но не качество генерации, ASR, TTS, живой урок или scoring.
DEV, PROD и live acceptance отдельно.

## 9. Риски и незакрытые решения интервью

1. Версия показанного задания нужна для честного разбора ответа. После выдачи текст неизменяем;
   исправленное условие получает новую связанную версию. Срок хранения следует privacy/reset
   правилам учебных данных. Точная схема хранения — инженерное решение после утверждения плана.
2. Неоднозначный материал может создать ложную ошибку. Валидатор формы её не обнаружит во всех
   случаях; смысловую проверку выполняет AI в SP-13B и во время урока.
3. ASR может исказить короткую фразу. Без надёжного источника AI не выдаёт уверенный негативный
   вывод; SP-13A не заявляет, что детектор ASR уже существует.
4. Представление аудио/скрипта, хранение персональных деталей и технический fallback требуют
   минимального набора данных и проверки в SP-13B/15. Изолированный контракт не доказывает UX.
5. Совместный merge может затронуть `FoundationService.kt`, `FoundationRoutes.kt`,
   `foundation_client.py`, `architecture.md`, `ai_docs/README.md`, `ai_docs/status.md`;
   точный список сообщить родителю после утверждения. Worktree соседей не редактировать.

## 10. Реализация и evidence · 2026-11-17

V55 и отдельный `LearningContent` domain реализуют неизменяемые версии, выдачу в regular Lesson,
отметку дефекта, scoped чтение/историю и privacy cleanup. Kotlin валидатор проверяет форму и
исторический StageRef через SP-12A. Python FoundationClient имеет read/write adapter.
Синтетические [JSON-примеры](../../content-contract/v1/examples.json) покрывают четыре метода,
альтернативные ответы и непригодное условие; Kotlin unit test проверяет их форму.
Точный [контракт/handoff](../integrations/learning-content.md) отделяет описание допустимых
ответов от оценки фактического ответа AI-репетитором.

Локально прошли 705 Python tests; 324 Kotlin unit tests; 118 PostgreSQL integration tests,
включая 3 новых Content scenarios; 2 новых HTTP Python → Ktor → PostgreSQL tests;
Kotlin `:server:buildFatJar detekt`. V55 применена только к отдельной PostgreSQL 14.10.
Тестовый каталог и материалы синтетические. SP-13B generation/semantic validation,
SP-14/15 voice execution, SP-17C Action Observations, Score и живой урок не проверены.
Commit/push/PR/merge/deploy не выполнялись; интеграцию ведёт родитель.
