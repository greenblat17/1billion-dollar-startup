# Telegram monitoring for scaling

Status: implemented locally on the PR #31 branch; DEV and PROD rollout not performed. Python tests: 267 passed. `./gradlew :server:test detekt`: passed. Scope: extend the Telegram-only Grafana dashboard in PR #31.

## Definitions

- All new series have bounded labels such as `client`, `stage`, and `outcome`. Never put a chat ID, message ID, job ID, transcript, exception text, or model response in a Prometheus label.
- The dashboard's operational windows are 5 and 15 minutes. Existing daily counters remain daily Moscow-time totals; they are not treated as monotonic Prometheus counters across midnight.
- One Telegram voice response starts when the accepted voice update enters the Ktor handler and ends only after Telegram acknowledges the final voice or text reply. Its duration includes both queues, download, AI work, and delivery. It excludes Telegram's time before the webhook is received. Hints, duplicate updates, and requests rejected before processing are not successful voice responses.
- Queue wait is the sum of time waiting for `TelegramChatActions`' per-chat action lock and for `SessionClipQueue` to start processing. Preparation and Telegram file download are part of total response time, not queue wait.
- A stage attempt is one logical STT, LLM, or TTS operation after its internal retries, or one logical delivery of the resulting Telegram reply. `failure / (success + failure)` is calculated separately per stage; these denominators are not the same population. A no-speech clarification is a successful STT operation, not a technical error. The delivery stage is counted once per reply, even if the reply has auxiliary cards.

## Implementation

1. **Availability and freshness.** Restore a compact service-health row using the existing `probe_success{job="blackbox-ktor"}` and `probe_success{job="blackbox-ai"}`. Add `up{job="speaking-v2"}` and the age of the last successful Telegram `speaking_dau` scrape. Label the latter as metrics freshness, not user activity. A missing series must remain visibly unavailable rather than become zero. Prometheus currently checks health every 15 seconds and scrapes AI metrics every 60 seconds. Show a warning after roughly three missed AI scrapes.
2. **Ktor measurement and scrape.** Add a small process-local, thread-safe Prometheus registry shared by the Telegram handlers and a new read-only endpoint on the localhost `MONITORING_PORT` connector. Hide the endpoint from OpenAPI and keep it out of the public Nginx locations. Add a Prometheus job for that endpoint in `infra/monitoring/deploy-remote.sh`. Keep labels bounded. A Ktor restart resets these process counters; Prometheus retains their scraped history.
3. **Reply and queue latency.** Instrument `TelegramChatActions.run` at admission and action-lock acquisition, `SessionClipQueue.submit` at admission and processing start, and `TelegramHandlers.voice/deliver` at receipt and acknowledged reply. Export classic histogram buckets, count, and sum for `telegram_voice_response_duration_seconds` and `telegram_voice_queue_wait_seconds`. Count delivered, failed, and queue-full voice requests separately. Render p50 and p95 over 15 minutes with a visible sample count; show no sample instead of a fabricated zero when there were no delivered replies.
4. **Recent errors and failure share.** Add monotonic `speaking_stage_attempts_total{client="telegram",stage,outcome}` for AI-stage operations in ai-service and Telegram reply delivery in Ktor. Instrument all success and terminal failure exits, including onboarding STT/TTS paths and internal retries; retries within one logical operation do not multiply the denominator. Export the AI counters alongside `/internal/metrics/prometheus` and the Ktor counters from the new endpoint. Use `increase(...[5m])` and `increase(...[15m])` for recent failures; calculate each stage's failure percentage only when its window has attempts. Keep the existing daily error breakdown for diagnosis, but label it as daily. Add a separate overall voice outcome count so queue rejection and failures before STT do not disappear from the operational view.
5. **Engagement.** Add `Ходов на активного пользователя` as `speaking_turns{client="telegram"} / speaking_dau{client="telegram"}`, guarded against DAU zero. The value is today's average completed voice turns per active Telegram user, not a per-user frequency distribution. Rename `Частота` to `Действия за день`. D1 return is already calculated from activation and daily activity events in `/admin/metrics/streaks`; verify its cohort definition and display there rather than deriving it from Grafana's 24-hour counters or exporting user IDs.
6. **Dashboard and documentation.** Group health, latency, failures, engagement, and cost so the first screen answers whether users can get timely replies. Add units (seconds, percent, count, USD), legends, and concise panel descriptions. Keep all product panels Telegram-only. Document metric definitions, scrape cadence, daily resets, missing-data behavior, and the distinction between operational monitoring and D1 cohort retention in `ai_docs/integrations/2026-10-02-monitoring.md`.
