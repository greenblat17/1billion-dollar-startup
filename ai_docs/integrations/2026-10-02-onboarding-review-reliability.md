# Onboarding review reliability

Status: integrated into `feature/telegram-onboarding-polish`; not deployed.

The final onboarding review requests an OpenRouter-compatible strict JSON Schema for the two verified compatible models, `google/gemini-3.5-flash-lite` and `openai/gpt-4o-mini`; provider routing requires support for the format. `openai/gpt-5.6-luna` has no compatible provider for this request on the tested OpenRouter route, so other configured models retain JSON-object mode. In every mode, the service rejects a response stopped by the completion-token limit, checks the exact required shape locally, and applies the existing band/position parser. The service does not save or show a partially valid report.

The first request allows 2400 completion tokens; if it fails, one automatic request allows 3200. The higher ceilings accommodate two-sentence skill summaries, explanations for up to five verified examples per skill, and optional Vocabulary alternatives. They are limits, not fixed output lengths; the effect on actual token use and retry frequency needs a DEV check. The strict schema and local shape check require these new fields, while the Vocabulary filter still rejects weak or ungrounded suggestions. Set `ONBOARDING_REVIEW_MODEL` for the primary review model and `ONBOARDING_REVIEW_FALLBACK_MODEL` for the second request; when unset, the review uses `LLM_MODEL` and retries that same model. Ordinary dialogue and live correction models remain separately configured. A DEV comparison can set the review model to `google/gemini-3.5-flash-lite` and the fallback to `openai/gpt-4o-mini` without changing ordinary conversation.

The second request happens only after an invalid or unavailable first response. It increases latency and provider cost only on that failure path. If both requests fail, the attempt remains `pending` with its accepted turns and explicit Retry. No fabricated CEFR or skill score is emitted. Provider calls can still fail twice, so the guarantee is that the service never publishes an invalid review, not that a review is always available immediately.

The final closing voice has its own short callback request, given only the last learner transcript. It starts alongside the assessment work; the review's callback field is kept as `null` for contract compatibility and is not used for speech. The callback is checked against the last transcript before TTS. TTS and the assessment plus memory branch run concurrently; the first result waits for both. When the assessment fails, the closing voice is still sent once with a Retry prompt. Retry uses the saved turns to regenerate only the assessment and memory, returning a text-only result. A stale Retry after completion is ignored. If callback generation fails or is not grounded in the last answer, the standard closing line is used.

The prompt also forbids treating an immediate self-correction as a learner error and forbids claims about speaking pace or hesitation without timing evidence. These rules reduce known mistakes but do not replace human review of assessment quality. See the [model comparison](../plans/2026-10-02-onboarding-review-model-comparison.md) for synthetic and two saved DEV-attempt probes. Before enabling a new primary model on DEV, inspect additional real outcomes and the complete Telegram retry flow. No raw DEV transcript belongs in the repository or CI logs.
