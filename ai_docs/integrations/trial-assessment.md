# SP-07: Post-Trial Assessment

SP-07 принимает решение о первичной диагностике после Trial v5.5. SP-03 хранит результат;
SP-17B остаётся владельцем Observations. Генерация Roadmap и показ в Telegram принадлежат
SP-08/11A и здесь не выполняются.

## Путь и границы

`trial.observe` применяет текущий batch через SP-17A. Только после успешной транзакции он
ставит `trial.assess` с ID observation job и transcript revision. Ошибка, retry или stale
`trial.observe` не запускает оценку. Assessment читает все страницы текущих active Trial
Observations и опубликованную версию каталога, использованную в них. Другой source revision,
набор Observations или каталог supersede результата. При пустом исправленном batch сохраняется
версия каталога прежней оценки, чтобы её Topics можно было перевести в Unknown. Повтор одного
job не создаёт второй оценки.

Python `TrialAssessment` применяет проверяемое ограничение: для конкретного Skill model может
предложить один CEFR только при двух разных независимых usable attempts и без противоречащих
наблюдений по одному Topic. При меньшем покрытии остаётся Unknown. Общий уровень не является
средним: он допустим только при оценке хотя бы двух Skills и должен совпадать с одним из их
уровней. Model вправе оставить любой уровень Unknown. Системный Listening всегда Unknown,
самооценка остаётся отдельно. Эти пороги — консервативное инженерное ограничение, не
калиброванная педагогическая шкала; живые кейсы должны проверить его качество.
Если модель всё же предлагает уровень без достаточных допустимых попыток или ссылок на две
разные попытки, Python понижает только этот Skill до Unknown и записывает безопасную
диагностику Skill и числа попыток. Overall также становится Unknown, если после этого
подтверждены менее двух Skills. Некорректные, чужие или устаревшие ссылки на Observations
по-прежнему отклоняют весь результат; Ktor повторно проверяет источники при записи.

Topic Knowledge строится только для наблюдавшихся Topic ID той же версии каталога:
два независимых правильных ответа без ошибок дают `Known`; две независимые неисправленные
ошибки без правильного ответа дают `Not Known`; одна ошибка или самокоррекция дают
`Presumed Not Known`; единичный успех либо конфликт дают `Unknown`. Подсказки, uncertain ASR,
повторы одной попытки и отсутствие ответа не создают подтверждённого вывода.
Ненаблюдавшиеся темы остаются `Unknown` в SP-03 по умолчанию. Уровень Topic не объявляет все
темы выше него незнакомыми. Сводка `coverage` в результате job считает пригодные
Observations без Topic ID и непригодные источники для контент-ревью, без вымышленных ID.

Ktor в одном fenced `job.apply` под student lock сверяет входной Observation job, точный
набор ID и revisions, актуальность источников и разрешённые выводы. Он применяет профиль
через `StudentLearningState` и Topic Knowledge через `StudentTopicKnowledge`; источники
ссылаются на `learning_observation` revision, без копии transcript. Перед записью он сверяет
SP-03 revision и чужой provenance. Изменение состояния после compute supersede job и не
перезаписывается. И `GET /learning-state`, и `GET /learning-state/topics` доступны будущему
SP-08; `GET /trial/events` показывает `assessmentStatus`.
Если исправление Trial источника убирает прежние Observations, SP-07 переводит собственные
прежние Topic оценки и системные уровни в `Unknown`, сохраняя историю. Узкий SP-03 путь
такого сброса допускает пустой список источников только для системных `Unknown`.

## Проверка и пределы

Локальные Python fixtures проверяют частичный результат, все четыре Topic состояния,
Listening Unknown, сохранение self-report и отказ от неподкреплённого уровня. PostgreSQL
интеграция проверяет fail/retry observation job, единственный assessment job, fenced apply,
передачу результата в SP-03 и защиту новой оценки. Синтетический HTTP тест проводит
Python → Ktor → PostgreSQL с частичным результатом. Fixture-тесты проверяют контракт,
не качество LLM на естественной речи, ASR или полноту Telegram Roadmap. Живой Trial,
DEV/PROD и дальнейший SP-08/11A handoff остаются отдельной приёмкой.
