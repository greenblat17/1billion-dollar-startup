# Повторный нагрузочный тест с длинными голосовыми, 14 октября 2026

**Среда:** DEV CMP → очередь → AI → реальные STT/LLM/TTS → загрузка аудиоответа в CMP. Telegram webhook и отправка ответа пользователю в тест не входят. Развёрнута версия `1d18344`. k6 подавал два реальных OGG/Opus клипа LibriSpeech длительностью 16,267 и 23,267 с попеременно. После завершения подачи генератор дождался ответов. В каждом прогоне пропущенных итераций не было.

Метрика ответа клипа в k6 включает и неуспешные HTTP-ответы; в основном прогоне 2 из 1201 измерений завершились 502. Время AI job по 1199 завершённым клипам: p50 **9,31 с**, p95 **12,04 с**, максимум **49,41 с**. p95 этапов внутри AI: STT **1,80 с**, сбор контекста **0,32 с**, LLM-ответ **4,86 с**, TTS **5,88 с**, notes **2,05 с**. За период не зафиксировано неуспешных LLM-вызовов; у всех 3592 успешных ответов были данные `usage`.

### TPM и TPS

Токены берутся из полей `prompt_tokens` и `completion_tokens` ответов OpenRouter для нагрузочных сессий. [`analyze-llm-usage.py`](../../analyze-llm-usage.py) суммирует их и находит максимальную сумму за скользящие 60 секунд по времени завершения вызова. Пиковое окно основного прогона закончилось **07:04:09.849 UTC**: 1 659 989 входных + 184 840 выходных = **1 844 829 токенов/мин**. Выходной TPS — 184 840 / 60 = **3080,67 токена/с**. Это совокупная пропускная способность параллельных вызовов; скорость генерации одного ответа отдельно не заявляется.

Из 3592 LLM-вызовов: notes — 1198, onboarding — 1192, reply — 1202. Расход по назначению сохранён в [`token-summary.json`](10rps-2m/token-summary.json). Продуктовая аналитика исключает нагрузочные сессии; в этих числах учтены только ответы с идентификатором данного прогона.

### Два HTTP 502

k6 получил два 502 на этапе отправки клипа около **07:04:00 и 07:04:10 UTC**. Сохранённые в Loki логи CMP показывают `ClipUploadFailure` с причиной `java.io.IOException: unexpected end of stream`: OkHttp получил EOF при `readResponseHeaders`, то есть ждал первую строку ответа AI. За весь интервал AI зарегистрировал **1199 ответов 202** на `POST /v1/clips` — ровно столько же, сколько успешных клипов у CMP. Не зафиксированы рестарт или OOM AI-контейнера, ошибки AI около этих двух моментов и сообщения ядра о нехватке соединений.

**Наиболее вероятный механизм — повторное использование уже закрытого TCP-соединения.** Работающий Uvicorn 0.35.0 закрывает неактивное HTTP-соединение через **5 с** (значение `timeout_keep_alive` по умолчанию; запущен без переопределения). CMP создаёт `HttpClient(OkHttp)` без настройки пула; в установленном OkHttp 5.3.2 время хранения свободного соединения по умолчанию — **5 мин**. Проверка с CMP-хоста: первый `GET /health` по одному TCP-сокету дал HTTP 200, а после 6 с простоя повторное чтение из этого сокета вернуло EOF. На границе закрытия сервера и повторного использования клиентом это может давать редкий `unexpected end of stream`.

Данных о номере TCP-соединения у двух ошибочных запросов нет. Поэтому **несовпадение тайм-аутов и точка обрыва установлены, но именно этот механизм для обеих ошибок не доказан**; альтернативный разрыв на сетевом пути исключить нельзя. Для проверки гипотезы нужен захват TCP-событий на CMP и AI при повторе либо выравнивание времени жизни соединений с повторным тестом. Порог `clip_failed == 0` не выполнен, k6 завершился с кодом 99. **Это частично успешный нагрузочный тест, а не подтверждение безошибочных 10 RPS на длинных голосовых.**

При одном снимке во время основного прогона CPU AI-контейнера составлял **276,41%** (сервер с 4 CPU), CMP **47,47%**, Redis **1,92%**. Это точечное наблюдение, не среднее за прогон. Баланс OpenRouter: **$14,21** перед разогревом, **$13,48** после него, **$4,43** после основного прогона. По завершении исходный `.env` DEV CMP восстановлен; `/health` вернул 200, тестовый маршрут — 404.

### Последующая бесплатная проверка HTTP-клиента

После этого DEV-прогона время хранения свободных соединений CMP с AI сокращено до **3 с** в локальном коде. [Тест пула](../../../cmp/server/src/test/kotlin/com/eliteteam/speakingcoach/AiHttpClientConnectionTest.kt) подтвердил повторное использование активного соединения и открытие нового после 4 с простоя. [Локальный нагрузочный тест](../../../cmp/server/src/test/kotlin/com/eliteteam/speakingcoach/AiHttpClientMockLoadTest.kt) с `MOCK_AI_LOAD_SECONDS=120` выполнил **1200/1200** циклов отправки клипа, опроса статуса и скачивания ответа через `HttpClipClient` при **10 RPS × 2 мин**. Оба теста прошли; поддельный AI работал на `127.0.0.1`, внешние провайдеры не вызывались, стоимость — **$0**. Эта версия CMP ещё не развернута на DEV; локальный результат относится только к HTTP-клиенту, а не к производительности реальных STT/LLM/TTS.
